# Deploying Proq

The app is two pieces deployed to two hosts:

| Piece | Host | Why |
| --- | --- | --- |
| **Frontend** (React + Vite SPA) | **Vercel** | Static build, instant CDN |
| **Backend** (FastAPI) + **Postgres** | **Render** | Long-running server for AI extraction / supplier-search background jobs that serverless can't run; managed Postgres replaces the local SQLite file |

The repo is an **npm-workspaces monorepo**: the frontend is `apps/web`, the
backend is `apps/api`, and new apps go under `apps/`. Both hosts build from the
repo root and are pointed at the right workspace — Render via `rootDir` in
`render.yaml`, Vercel via the build command in `vercel.json`.

> **Why not all on Vercel?** The backend uses a real database, writes uploaded
> plan PDFs to disk, and runs background extraction/search jobs *after* sending
> the HTTP response. Vercel's serverless functions are ephemeral (no persistent
> filesystem) and freeze once they respond, so the backend needs a normal
> long-lived host. Render (or Railway / Fly.io) is that host.

Deploy the **backend first** so you have its URL when configuring the frontend.

---

## 1. Backend + database → Render

The repo ships a [`render.yaml`](render.yaml) Blueprint that provisions the web
service **and** a managed Postgres database in one shot. It sets
`rootDir: apps/api`, so Render builds the backend workspace and never touches the
Node frontend at the repo root.

1. Push this repo to GitHub (already done if you're reading this from it).
2. Go to <https://dashboard.render.com> → **New** → **Blueprint** → select this repo.
3. Render reads `render.yaml`, shows the `procureai-api` service + `procureai-db`
   database, and asks you to fill the secret env vars (`sync: false`). For a first
   deploy you can leave the optional integration keys blank — the app runs with
   clearly-flagged **mock** AI extraction / supplier search until you add them.
   - `PROCUREAI_CORS_ORIGINS` — leave blank for now; set it in step 3.
4. Click **Apply**. Render installs deps, runs `alembic upgrade head`, then starts
   uvicorn. When it's live you'll get a URL like `https://procureai-api.onrender.com`.
5. Verify: open `https://procureai-api.onrender.com/health` → `{"status":"ok"}`.

### Required env vars (set automatically or in the dashboard)

| Var | Source |
| --- | --- |
| `PROCUREAI_ENV` | `production` (set by `render.yaml`) — refuses to boot with the default JWT secret; keeps demo data/accounts out |
| `PROCUREAI_DATABASE_URL` | auto-injected from the Render Postgres |
| `PROCUREAI_JWT_SECRET` | auto-generated by Render |
| `PROCUREAI_CORS_ORIGINS` | **you set this** — JSON array, e.g. `["https://your-app.vercel.app"]` |

> Deploying to **Railway** instead? Set `PROCUREAI_ENV=production`,
> `PROCUREAI_JWT_SECRET`, and `PROCUREAI_CORS_ORIGINS` manually in the service
> variables — Railway has no equivalent of the Blueprint's `generateValue`.
> Note the GitHub Actions CD job deploys to **Railway**; the Render Blueprint
> path is for manual/one-off deploys.

### Optional integrations (blank ⇒ mock / log-only)

| Var | Enables |
| --- | --- |
| `PROCUREAI_OPENAI_API_KEY` | real GPT-4.1 plan/BOM extraction |
| `PROCUREAI_GOOGLE_MAPS_API_KEY` | real supplier discovery (Geocoding + Places) |
| `PROCUREAI_GMAIL_*` | real RFQ email send / quote ingest. `PROCUREAI_GMAIL_SENDER_ADDRESS` is the single From address for **all** outbound mail (users are Cc'd, never used as the sender) — set it to the account you minted the token for. See [docs/email-setup.md](docs/email-setup.md). |

### A note on uploaded files

By default files are stored on the service's local disk. The free plan has no
persistent disk, so **extracted BOM data persists in Postgres** but the **raw
uploaded PDFs are lost on each redeploy**. Two ways to keep them:

1. **Recommended — S3-compatible object storage** (AWS S3, Cloudflare R2, or
   MinIO): set `PROCUREAI_STORAGE_BACKEND=s3` plus `PROCUREAI_S3_BUCKET`,
   `PROCUREAI_S3_ACCESS_KEY_ID`, `PROCUREAI_S3_SECRET_ACCESS_KEY`, and (for
   R2/MinIO) `PROCUREAI_S3_ENDPOINT_URL`. Uploads survive redeploys and
   previews redirect to short-lived presigned URLs. Files uploaded before the
   switch keep working (the backend is chosen per file).
2. Upgrade the service to a paid plan and attach a disk — the exact two-step
   change is documented inline at the bottom of [`render.yaml`](render.yaml).

## 1b. Backend + database → Railway (alternative to Render)

Railway is an equally good fit (long-running server + managed Postgres). The repo
ships [`apps/api/railway.json`](apps/api/railway.json) so the build/start settings
are baked in.

> ⚠️ **Monorepo migration — one manual step.** The backend moved from `backend/`
> to `apps/api/`. Railway's **Root Directory** is a dashboard setting that no
> config file can override, so you must update it by hand: **Settings → Root
> Directory** → change `backend` to **`apps/api`** → redeploy. Until you do, the
> next backend deploy **will fail**.
>
> While you're in Settings, check **Config-as-code / config file path** too. Per
> Railway's docs the config file *does not* follow Root Directory — if a path is
> set there it needs the absolute form **`/apps/api/railway.json`**, not
> `/backend/railway.json`. If the field is blank, leave it blank.
>
> Both deploy triggers root the build at the repo root, so `apps/api` is the
> correct value in every case: a GitHub push makes Railway clone the whole repo,
> and the CD job runs `railway up` from the repo root as well (see the note in
> `.github/workflows/ci-cd.yml`). Deploying from inside `apps/api` instead would
> require Root Directory to be *empty*, and the two triggers would silently
> disagree — which is exactly why the job doesn't do that.

> **Repo not showing in Railway's list?** That's GitHub App access, **not** a
> missing config file. In Railway click **Configure GitHub App** → on GitHub grant
> the Railway app access to `procurementAgent` (or *All repositories*) → Save, then
> refresh. A config file can't make a repo appear — Railway must be able to see it
> first.

1. **New Project** → **Deploy from GitHub repo** → select `procurementAgent`.
2. In the service's **Settings → Root Directory**, set **`apps/api`**. This is the
   one setting that *can't* live in the config file, and it's required — otherwise
   Railway builds the Node frontend at the repo root and fails. Railway then reads
   `apps/api/railway.json` for the rest (Nixpacks build, `alembic upgrade head` +
   uvicorn start, `/health` check, Python pinned via `apps/api/runtime.txt`).
3. **Add a database:** in the project, **New → Database → PostgreSQL**.
4. **Map the DB URL** (the one gotcha): Railway's Postgres exposes `DATABASE_URL`,
   but the app reads the prefixed name. In the API service's **Variables**, add:
   ```
   PROCUREAI_DATABASE_URL = ${{Postgres.DATABASE_URL}}
   ```
5. Add the remaining variables (same names as the Render table above):
   `PROCUREAI_JWT_SECRET` (any long random string), `PROCUREAI_CORS_ORIGINS`
   (JSON array of your Vercel URL — set after step 2 below), and optionally the
   `PROCUREAI_OPENAI_API_KEY` / `PROCUREAI_GOOGLE_MAPS_API_KEY` / `PROCUREAI_GMAIL_*`
   keys (blank ⇒ mock behaviour).
6. Deploy → **Settings → Networking → Generate Domain** to get the public URL.
   Verify `https://<your-app>.up.railway.app/health` → `{"status":"ok"}`.

For persistent uploaded PDFs, attach a **Volume** mounted at `/data` and set
`PROCUREAI_UPLOAD_DIR=/data/uploads` (same caveat as Render — BOM data is in
Postgres regardless).

Wherever the backend lives (Render **or** Railway), the Vercel step below is
identical — just point `VITE_API_URL` at that backend's URL.

## 2. Frontend → Vercel

1. Go to <https://vercel.com/new> → import this repo.
2. Vercel reads [`vercel.json`](vercel.json) at the repo root, which builds the web
   workspace (`npm run build --workspace @proq/web`) and serves
   `apps/web/dist`. Leave the defaults — in particular, leave the project's
   **Root Directory** setting **unset (the repo root)**; the monorepo build is
   driven by `vercel.json`, not the dashboard.
3. Add **one** Environment Variable:
   - `VITE_API_URL` = your Render backend URL (e.g. `https://procureai-api.onrender.com`)
     — **no trailing slash**.
4. Deploy. You'll get a URL like `https://your-app.vercel.app`.

> `VITE_API_URL` is read at **build time** ([apps/web/src/api.ts](apps/web/src/api.ts)).
> If you change it later, trigger a redeploy so the new value is baked in.

---

## 3. Connect the two (CORS)

Back on the backend host (Render or Railway), set `PROCUREAI_CORS_ORIGINS` to a
JSON array containing your Vercel URL and save (this redeploys the backend):

```
["https://your-app.vercel.app"]
```

Include every origin you'll hit the API from — add your custom domain and/or
Vercel preview URLs as additional array entries if needed.

That's it. Visit the Vercel URL, register an account, and the frontend will talk
to the backend.

## Local development

```bash
# backend (defaults to zero-config SQLite; optional local Postgres via docker compose)
cd apps/api && pip install -r requirements.txt && uvicorn app.main:app --reload

# frontend (proxies to http://localhost:8000 by default) — run from the repo root
npm install && npm run dev
```
